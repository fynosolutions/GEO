# Backend

`public.ts` exposes shared entry points to CLI/HTTP callers. `collection.ts` owns identity checks, field mapping, category-specific schemas, one output file and Apify URL discovery. `apify.ts` owns bounded Actor runs, pagination and remote cancellation, including a cancel/start acknowledgement race. Browser collection is temporarily disabled; `browser.ts` retains URL/domain validation helpers and the dormant adapter. Field values retain source types and structures except the requested Facebook Not yet rated to numeric zero conversion.

The catalogue has ten platforms. Original eight listings retain rating/review_count; Resy and Instagram profiles omit those keys and include followers/posts instead. Missing profile counts remain null. The eight listing platforms include rating_raw with original rating and review count together (separate source fields are combined as average/count without value conversion); Resy and Instagram omit it; rating_value and review_count_value remain excluded. See the contract for profile identity evidence and category metadata.

`cli.ts` is the main entry: name/place ID to `out/<restaurant-name>.json`. `audit.ts` persists local visualization jobs; `server.ts` serves that UI and downloads the generated file. `auth.ts` retains the optional existing token gate; no user database or tenant/subscription model exists. `config.ts` loads `.env` and explicit proxy variables without Windows registry access.

`batch.ts` validates a full restaurant list, orchestrates sequential store collection and writes one file per restaurant in a unique out/batches/ directory. Every file has exactly the same array/schema as single-store collection (ten selected platform records by default); input/store_id metadata stays in local job state. Resolved-name changes rename the initial placeholder rather than leaving duplicate files, and duplicate/case-insensitive names receive safe id suffixes. Per-store intermediate output goes to ignored .local/batches/. cli.ts --stores and the web list mode share this orchestration. audit.ts persists batch progress through the same cancellation controls. errors.ts keeps export reasons concise while provider diagnostics retain detailed evidence. This is independent of weekly history and does not rewrite stores.json or historical snapshots.

See [the contract](../docs/API_CONTRACTS.md) and [Actor setup](../docs/APIFY_SETUP.md). Original responses and screenshots are diagnostics under `.local/` and never part of the exported schema.

The current input supports optional platforms. Google identity resolution is mandatory; only selected platforms are queried/emitted afterwards. matched:false records contain no unconfirmed business data. Source values are unchanged on successful matches.

Yelp verifies at most three distinct listing candidates per target (one attempt and two retries). It can use one supplemental Apify SERP search for more candidate URLs when needed; that search keeps the full Google-resolved name/address, and the target identity is never replaced by a different branch. The Yelp Actor only receives business URLs: its native and search-URL modes were observed rewriting US searches to the UK domain and failing. Duplicate URL variants do not count as new candidates.

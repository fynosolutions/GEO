# 开发与协作规范

## 实施顺序

当前已确定 F1 技术与接口基线，见 F1_IMPLEMENTATION.md 和 F1_HANDOFF.md。后续任务按 AGENTS.md 读取当前约束，并检查现有代码，不重新选择一套技术栈或商家数据模型。

先确认技术栈与持久化方案，落实 F1 数据模型和公开读取边界，再逐步实现检测、优化、报告。需求阶段不等同于实现完成；后续功能计划维护在 ROADMAP.md。

## 目录与依赖

- app/ 负责页面入口和交互，业务判断在 modules/。
- 模块通过 public.ts 显式导出公开能力，不跨模块导入内部实现或直接读写对方数据表。
- infrastructure/ 负责数据库、存储与外部服务适配，不定义业务指标。
- shared/ 仅容纳无特定业务归属且确有复用需求的代码，不反向依赖业务模块。
- 模块内部在有实际需要时再细分文件夹，不提前生成空泛的多层架构。
- A1、B1 等编号保留在产品文档中，目录采用业务名称。

## 数据安全与历史

- 产品以美国餐馆和英文为基线，遵循 US_MARKET_BASELINE.md；开发文档可使用中文。不得从省区、公里、人民币等旧资料静默推定美国州、英里或美元。
- 不重复维护商家主数据，不静默把渠道信息覆盖到标准事实。
- 修改商家资料时保留历史及证据，检测和报告引用当时版本。
- 明确公开数据和内部服务档案边界；外部模型调用仅使用允许外发的资料。
- 不提交密钥、真实商家数据、数据库文件或备份文件。
- 数据库变更记录到 database/migrations/，说明兼容性和恢复方式。

## 开发协作

- 明确每次改动所属模块与验收目标，减少无关改动。
- 公开接口调整时同步更新 API_CONTRACTS.md，并检查调用方。
- 保留现有用户文件；调整目录用途时同步更新该目录 README.md。
- 不为了目录占位创建不可用功能、伪造数据或无意义测试。

## 验证与交付

按变更风险执行必要验证。跨模块测试优先覆盖版本追溯、证据关联、失败统计、复测可比性和备份恢复；模块内部测试可与实现相邻放置。

技术栈确定后在根 README.md 补充安装、启动、构建、迁移和测试命令。交付时说明实际实现、验证结果及尚未完成的部分。

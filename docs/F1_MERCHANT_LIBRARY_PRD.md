# F1 商家资料库产品需求文档

版本：V1.2 美国餐馆与英文资料基线  
日期：2026 年 10 月 19 日  
产品：餐馆 GEO 个人工作站  
使用者：独立完成商家建档、检测、优化、复测及报告的一名操作者

本版本按 [US_MARKET_BASELINE.md](US_MARKET_BASELINE.md) 调整为美国餐馆，工作站所有产品文字、目录和标准资料使用英文。开发说明可用中文，历史事实及原文证据保持忠实。公开契约升级为 f1.v2。

开发分工：本次先实现 F1 商家资料管理；检测、优化和报告等后续模块由其他开发者负责。开发者多人协作不改变工作站单人、免登录的使用方式。

F1 为每家餐馆建立可持续维护的资料档案，统一保存门店事实、素材、公开渠道记录和内部合作信息。后续 GEO 检测、信息一致性检查、修正任务和报告通过门店 ID 引用这些资料，不分别维护商家主数据。

F1 是共享数据的业务来源。11 类资料均需具有可供其他模块调用的结构化读取能力，不能只在页面中展示或只保存在浏览器表单里。其他模块按用途读取资料；“仅内部”限制公开导出和外发，不阻止工作站内部通过明确用途读取。

本期覆盖 11 类资料的人工录入、查询、编辑、核实、历史追溯及备份恢复。信息模型全面，首次建档只要求少量基础字段；资料可逐步补全。

## 1 产品目标与范围

### 1.1 产品目标

- 在一个工作站中管理多家餐馆，并明确区分品牌与具体分店。
- 将零散的商家信息整理为有唯一归属、可查询的结构化资料。
- 为关键事实保留核实状态、来源、时间和证据。
- 支持逐步补全资料，不阻止资料不完整的门店建档。
- 保留历史版本，使后续报告可以还原当时使用的事实。
- 提供持久化与完整备份，退出、刷新或重启后数据仍可读取。

### 1.2 已确定的产品前提

| 项目 | 本期约定 |
| --- | --- |
| 使用模式 | 单人操作，可管理多家门店 |
| 登录与账号 | 无登录、注册、账号、角色、人员分配和权限管理 |
| 餐馆参与方式 | 餐馆不直接操作系统，由操作者录入和维护资料 |
| 信息采集方式 | 人工录入、粘贴、上传文件和记录外部链接 |
| AI 依赖 | F1 不依赖 AI API，不要求自动提取或判断 |
| 技术栈 | TypeScript + Next.js App Router、SQLite + Drizzle、本地附件；确认方案见 F1_IMPLEMENTATION.md |
| 工作站导航 | 商家资料库为可用模块；检测、优化、报告可先提供待开放入口 |
| 数据使用 | 后续模块通过 `src/modules/merchant/public.ts` 读取 F1；不复制主数据、不直接访问 F1 内部表 |
| 对接依据 | 模块调用、数据状态、版本与错误约定见 [API_CONTRACTS.md](API_CONTRACTS.md)，属于 F1 交付的一部分 |

### 1.3 本期交付

1. 工作站基础布局、导航和当前门店上下文。
2. 商家列表、新增、详情、分组编辑、搜索、筛选、归档与恢复。
3. 本文 11 类信息的基础录入能力；重复内容使用明细列表。
4. 字段填写状态、核实与证据、公开范围、有效期和修改历史。
5. 菜单菜品、营业时段、包间、价格、渠道快照和素材的关联管理。
6. 场景标签及其依据管理。
7. 完整备份、校验与恢复；可公开资料导出。
8. 可实际调用的跨模块读取接口、对应数据契约、虚构样例和最小调用示例；不以接口占位文件作为交付。

### 1.4 本期不实现

- 多人协作、账号权限、员工绩效、商家自助后台。
- 支付订阅、自动收费、财务核算和完整 CRM。
- AI 自动问答、自动爬取、自动生成文案、自动发布与平台账号登录。
- A1 的检测批次、回答和提及率计算。
- B1 的自动一致性判定、修正任务和执行工作流。
- 前后复测计算与完整 GEO 报告生成。
- 点餐、订单、库存、收银和消费者档案。

## 2 核心概念与 MECE 归属

### 2.1 核心对象

| 对象 | 定义 |
| --- | --- |
| 品牌 | 可被多家门店关联的品牌身份；本期提供轻量品牌选择与新增，不建设独立品牌运营模块 |
| 门店 | 一家具有具体经营地点或明确服务范围的餐馆，是 F1 的核心对象 |
| 商家资料 | 某门店的业务事实、内容资产、渠道记录及内部服务档案的集合 |
| 标准事实 | 操作者维护的门店当前资料，核实状态独立记录；尚未核实不代表错误 |
| 渠道快照 | 某个外部页面在某次采集时展示的原始信息，不自动覆盖标准事实 |
| 证据 | 支撑一个或多个字段判断的文件、图片、链接或核实说明 |
| 场景标签 | 基于事实作出的适用场景判断，保存依据，不冒充客观事实 |

一条 `merchant_id` 对应一家具体门店。同品牌不同分店分别建档；门店名称和地址不是唯一 ID。品牌通用介绍由品牌维护，门店介绍只描述本店差异；门店需要引用品牌介绍时直接引用。

### 2.2 业务分类

| 编号 | 分类 | 唯一职责 |
| --- | --- | --- |
| M01 | 身份与品牌 | 确定是谁、属于哪个品牌、如何公开联系 |
| M02 | 位置与到达 | 描述地理位置、入口和到店路线 |
| M03 | 营业时间与状态 | 描述经营状态及何时营业 |
| M04 | 菜品与餐饮供给 | 描述提供什么餐饮产品 |
| M05 | 价格与交易条件 | 描述收费、优惠及支付条件 |
| M06 | 空间与设施 | 描述实体空间、容量和设施 |
| M07 | 服务与接待规则 | 描述服务能力和接待限制 |
| M08 | 资质与可信背书 | 描述可核实的资质、认证及背书 |
| M09 | 内容与媒体资产 | 管理图片、视频、文件和发布文案 |
| M10 | 公开渠道与外部表现 | 管理外部页面、快照和平台观测值 |
| M11 | 内部客户与服务档案 | 管理餐馆对接与本次服务关系 |

### 2.3 去重规则

| 信息 | 唯一存放位置 | 其他位置如何使用 |
| --- | --- | --- |
| 公共电话及其他公开联系方式 | M01 | 预约等场景引用联系方式 ID |
| 商家对接人的联系方式 | M11 | 不默认作为公开电话使用 |
| 品牌介绍与门店介绍 | M01 | M09 的发布文案记录独立改写版本及依据，不另存一份同义主资料 |
| 标准地址与定位 | M02 | 渠道上的地址另存 M10 快照 |
| 停车位置和路线 | M02 | 停车设施是否提供、容量归 M06，收费归 M05 |
| 标准营业时间 | M03 | 菜单和服务记录可引用营业时段；外部营业时间归 M10 |
| 菜品名称、规格、食材、份量 | M04 | 价格引用菜品规格 ID，照片引用菜品 ID |
| 菜品、套餐、包间等费用 | M05 | 对应对象页面可联合展示，不重复保存金额 |
| 包间容量与设施 | M06 | 价格引用包间 ID，预约规则归 M07 |
| 配送、自取、预约能力 | M07 | 对应平台链接归 M10 |
| 证照、奖项、报道的事实 | M08 | 证明文件引用 M09 素材，不再复制文件 |
| 所有媒体文件和文案版本 | M09 | 其他分类通过关联 ID 使用 |
| 平台评分与评价数 | M10 对应快照 | 不保存为门店永久评分或跨平台混合分数 |
| 优惠条款与有效期 | M05 | 宣传海报归 M09，平台活动页面归 M10 |
| 检测结果、修正执行、对比指标 | 后续对应业务模块 | 仅关联 `merchant_id` 和资料版本 |

同一事实只维护一处权威记录。跨分类引用允许在界面重复展示，但不能产生第二份可独立修改的主值。

## 3 页面与主要流程

### 3.1 页面结构

| 页面 | 核心内容与操作 |
| --- | --- |
| 商家列表 | 搜索、筛选、新增、最近修改时间、营业状态、合作状态、资料准备情况、归档入口 |
| 新增商家 | 输入最小建档字段，提示疑似重复门店，保存后进入详情 |
| 商家详情 | 基础摘要、11 类资料分组、场景标签、待核实提示、当前有效信息 |
| 分组编辑 | 只编辑当前组，支持新增明细、校验、保存和放弃 |
| 核实与证据 | 查看字段值、来源、证据、有效期，完成核实或标记争议 |
| 历史记录 | 按时间查看字段变化、明细变化、核实变化和历史资料版本 |
| 归档列表 | 搜索已归档门店、只读查看、恢复 |
| 备份与恢复 | 导出完整备份、选择备份文件、校验、显示恢复摘要、恢复结果 |

详情页顶端始终显示完整店名、分店名和地址摘要。切换门店会同步更新全部子页上下文；有未保存修改时，提示保存、放弃或留在当前页。

### 3.2 新增商家

1. 输入英文完整门店名称、市场区域、街道地址、主营菜系，并明确选择门店当地 IANA 时区；城市、州和 ZIP 可逐步补充。
2. 选择已有品牌、新增品牌，或明确选择独立门店。
3. 系统检查疑似重复记录，展示候选门店的名称、地址和电话。
4. 操作者选择查看已有记录或继续创建，不按同名自动合并。
5. 保存生成稳定 ID，进入详情页；其余信息显示未知或未填写。

### 3.3 维护与核实

1. 在详情中选择分组，填写或更新资料。
2. 对关键事实登记来源、采集时间及可用证据。
3. 单独执行核实操作；普通保存不自动将字段标为已核实。
4. 已核实的事实值发生变化后，新值默认回到未核实状态；旧值及其证据保留在历史中。
5. 保存生成新资料版本，刷新后仍可读取。

### 3.4 记录外部渠道

1. 为门店添加渠道页面，记录平台和链接。
2. 新增一次采集，录入当时页面显示的信息、采集时间及证据。
3. 保存为新快照；再次采集另建快照，历史不覆盖。
4. 需要修改标准事实时，另行编辑对应资料并核实，不从快照静默同步。

### 3.5 归档与恢复

归档表示工作站暂不维护该档案，不等于餐馆停业。归档后默认不出现在活跃列表，资料和历史仍保留；恢复后沿用原 ID。本期不提供门店永久删除和自动合并。

### 3.6 人工录入效率

- 基础建档为短表单，其他内容按组展开；显示本组未保存状态，避免一张超长必填表单。
- 周营业时间支持复制到其他星期；菜品、包间、联系方式和价格支持连续新增明细。
- 可将同一来源、采集时间、核实说明和证据应用到本次选中的多个字段；核实前列出所选字段和值，不能顺带核实未选内容。
- 已核实分组内仅修改一个字段时，只取消该字段或其依赖明细的核实状态，不重置整家门店。
- 支持直接录入原文或备注，但名称、地址、电话、时间、金额、容量等用于检索和比较的数据必须另有结构化值。
- 附件上传、粘贴链接和保存资料均为人工操作；不得在后台推断未知事实、自动联网补全或覆盖输入。
- 菜单图片可以先保存为素材，不强制一次性录入全部菜品；只有已录入的结构化菜品能供其他模块按菜品检索。

## 4 字段约定

### 4.1 必填与状态

- 建档必填：英文完整门店名称、市场区域、街道地址、至少一个主营菜系、品牌关系选择、门店美国 IANA 时区。
- 营业状态、联系方式、营业时间等允许未知，建档不因缺失被阻止。
- 重复明细中的“必填”仅在新增该明细时生效。例如，没有价格信息可以不建价格记录；新增记录后必须填写金额口径。
- 每个可选业务字段区分 `known` 已知、`unknown` 未知、`not_applicable` 不适用。未填写默认未知。
- 对是否有包间等布尔事实：已知且为否与未知不同；零、空字符串、空数组不得自动表示否。
- 核实状态独立于填写状态，采用未核实、已核实、存在争议。
- 未知和不适用不显示为零；不适用需记录简短原因。

### 4.2 类型与单位

金额使用十进制字符串及 USD，关联计价单位。日期保存 YYYY-MM-DD，营业时段保存本地 HH:mm 和门店 IANA 时区；新门店必须明确选择时区，不推定全美统一时区。面积新增 sq ft、配送距离新增 mi，份量明确 oz / lb / fl oz 等实际单位。旧金额、单位和时区不自动换算。多选标签可扩展，以英文维护。

### 4.3 系统字段

所有门店具有 `merchant_id`、当前资料版本、创建时间、最后修改时间、归档状态及归档时间。明细具有独立 ID 和所属门店 ID。单人版不设置创建人、负责人或修改人字段。

以下字段表为逻辑字段字典；最终技术字段名由数据契约统一规定。相关联的金额、素材和渠道均使用引用，不重复存储。

### 4.4 字段标识与扩展

每个公开字段、明细类型及枚举项具有稳定的机器标识。界面名称可以修改，机器标识不能随中文文案变化；其他模块不得使用中文标签、数组位置或展示顺序作为关联键。

所有明细均使用独立 ID。标准事实除结构化值外可保留人工输入原文，便于核对；标准化产生的显示值不覆盖原文。自定义菜系、标签等保留扩展项标识，不能靠随意增加数据库列支持扩展。

供联调使用的字段必须在 `API_CONTRACTS.md` 约定名称、类型、单位和状态。新增字段可向后兼容；重命名、删除和改变语义前同步契约并检查调用方。

## 5 商家信息字段字典

### 5.1 M01 身份与品牌

| 字段组 | 内容 | 规则 |
| --- | --- | --- |
| 门店名称 | 完整名称、分店名称 | 完整名称必填；分店名称用于同品牌门店区分 |
| 名称变体 | 简称、别名、外文名称 | 支持多条，记录语言及名称类型，用于后续实体匹配 |
| 曾用名 | 名称、使用起止时间 | 不直接等同于当前名称，保留历史 |
| 品牌关系 | 所属品牌 ID、独立门店 | 必须作出选择；品牌变更保留历史 |
| 品牌信息 | 品牌名称、别名、创立年份、品牌介绍 | 由轻量品牌记录统一维护，不复制到各门店 |
| 门店信息 | 门店介绍、开业日期 | 门店介绍描述本店；开业日期允许只知道年份或月份，保留精度 |
| 公共联系方式 | 类型、号码或账号、用途、主要标记 | 支持多条；用途可为咨询、预约等；默认属于可公开候选，仍需明确公开范围 |

英文主名称清理首尾空格，允许 Café 等带重音的拉丁名称。非英文原名保存在原文别名。美国电话录入十位号码或 +1 前缀，分机独立；不自动验证号码所有权。

### 5.2 M02 位置与到达

| 字段组 | 内容 | 规则 |
| --- | --- | --- |
| 美国地区 | US、City、两位 State / territory、ZIP / ZIP+4、County / parish / borough、市场区域 | 市场区域建档必填；其他结构化字段可逐步补充，ZIP 保留前导零；province / district 仅作旧数据兼容 |
| 详细地址 | 街道地址、建筑名称、楼层、铺位 | 详细地址必填；结构化补充字段可选，展示地址由其组合 |
| 商圈 | 主要商圈、辅助商圈 | 不用商圈代替行政地址 |
| 地理坐标 | 经度、纬度、坐标系、定位来源 | 经度和纬度成对填写；坐标系未知时不得跨地图直接换算 |
| 入口位置 | 入口说明、入口点位 | 入口照片引用 M09 |
| 地标与公交到达 | 附近地标、站点、地铁线路及出口、步行距离或时间 | 距离和时间记录计量单位及起点 |
| 驾车与停车到达 | 停车场位置、入口、停车后步行路线、临停上下客位置 | 容量归 M06，停车费用归 M05 |

### 5.3 M03 营业时间与状态

| 字段组 | 内容 | 规则 |
| --- | --- | --- |
| 经营状态 | 未知、筹备中、营业中、暂停营业、永久停业 | 与工作站归档状态分开 |
| 状态期间 | 生效日期、预计恢复日期、说明 | 暂停营业可填写恢复日期；预计日期不当作已恢复事实 |
| 时区 | 门店时区 | 用于解释营业时段和日期例外 |
| 周营业安排 | 星期、休息标记、全天营业标记、多个营业时段 | 全天、休息、具体时段互斥；支持午晚市 |

## 6 场景标签与依据

场景标签作为独立关联记录，组合前述事实，不复制事实字段。初始可提供商务宴请、家庭聚餐、朋友聚会、情侣约会、独自用餐、亲子用餐、夜宵、游客用餐等可编辑选项。

每条标签包含名称、适用或不适用或待判断、条件、依据字段引用、依据说明、确认时间和对应资料版本。自动读取事实可以辅助展示，不能自动将主观标签标为确认适用。

| 标签示例 | 可关联的事实依据 | 需保留的条件 |
| --- | --- | --- |
| 十人聚餐 | 桌型、包间容量、团体接待规则 | 是否需预约、适用日期、消费条件 |
| 夜宵 | 营业时段、最后点单、菜品供应时段 | 具体星期和时间范围 |
| 亲子用餐 | 儿童设施、儿童餐、接待规则 | 年龄和适用区域 |
| 商务宴请 | 包间、接待能力、费用和场景说明 | 预算、人数及判断依据 |

事实变化后，引用该事实的标签标记为待复核，保留此前判断历史。

## 7 核实 公开范围与历史

### 7.1 来源与证据

关键事实的元数据包含来源类型、来源说明或 URL、采集时间、核实状态、核实时间、核实说明、证据引用、适用条件、生效日期和失效日期。来源可选商家提供、电话确认、现场确认、公开页面和其他。

已核实至少需要核实时间和来源说明。电话或现场确认允许以文字核实说明作为证据，不强制提供截图。存在争议时必须说明争议原因，允许保留多个候选说法，但不静默选择其一为已核实事实。

对标量字段按字段核实；对营业时段、价格等明细按完整明细核实，避免出现仅核实一个金额却误认为全部价格条件都已核实。

未知表示尚不了解，不等于外部资料错误；不适用不参加需要该字段的完整度分母。资质或价格失效后，保留历史，当前展示标明失效，不继续作为当前有效的已核实事实供后续模块使用。

### 7.2 公开范围

每项资料和素材支持可公开、仅内部、待确认三个状态。内部档案固定仅内部；证照编号、证明文件默认待确认；其他事实初始待确认，操作者可在分组编辑时批量设为可公开。

本期没有对外访问入口，“公开范围”用于资料导出和后续内容发布选择，不是用户权限。可公开资料导出只包含明确标记可公开的当前资料，不包含内部备注、合同、对接人、待确认信息或默认的原始证据附件。完整备份则保留所有资料。

工作站内部业务读取与外发分别处理：检测、优化、报告可按明确用途读取所需档案及核实状态，不应因资料尚未标为可公开而无法内部核对。传给外部 AI、发布到渠道或生成对外资料时，必须选择可外发投影；不得直接把完整档案序列化后发送。

### 7.3 版本与追溯

- 每次实际改变资料的成功保存形成递增资料版本，至少记录变更时间、变更类型、对象、字段、前值和后值；无变化保存不产生空版本。
- 核实状态、公开范围、归档、恢复和标签判断的变化也记入历史。
- 关系型记录可使用变更日志加可恢复快照实现；不要求把所有数据强制存入通用字段值表。
- 后续批次可绑定 `merchant_id + profile_version`，读取当时资料，不能被当前编辑覆盖。
- 品牌信息等共享对象也需保留版本；门店历史读取必须解析当时引用的版本，不能用品牌当前值重写历史。
- 品牌资料变化时，受影响门店形成新的资料版本并绑定新的品牌版本；历史版本仍绑定旧品牌版本，不允许同一个门店版本返回两种不同资料。
- 编辑标准事实的版本与渠道快照的采集时点分别解释。后续批次需独立保存使用的快照 ID；按资料版本读历史时不混入后来新增的快照或素材。
- 资料版本固定原始数据；按日期判断是否营业、价格是否有效等结果还需固定适用日期。同事复现历史判断时同时保存版本、日期和门店时区，不用今天的有效性筛选代替当时条件。
- 历史查看只读。本期不提供单字段回滚；需要恢复旧值时重新编辑并产生新版本。

## 8 资料准备情况

不以“所有字段是否填满”评价餐馆。详情页展示以下独立状态，并可展开缺失项。

| 状态 | 判定规则 |
| --- | --- |
| 已建档 | 最小建档字段满足要求 |
| 核心资料已补齐 | 已知营业状态、公共联系方式、周营业安排、人均价格或明确不适用，以及名称别名核对结果 |
| GEO 基础核实已完成 | 名称、详细地址、营业状态、公共联系方式、周营业安排和主营菜系均已核实且当前有效；关键字段不能以不适用绕过 |
| 待办提示 | 展示未知、未核实、争议、已失效和依赖事实变更的标签数量 |

“名称别名核对结果”支持明确记录未发现其他别名，不能用空列表推断已经核对。各分类可展示已知项及适用项数量；集合类以是否完成该项采集声明计算，不因录入更多菜品而抬高整体准备状态。

暂停或永久停业门店仍可建档和核实，后续模块据此决定是否适合开展推荐检测，不虚构正常营业资料。

## 9 查询 校验与异常处理

### 9.1 搜索与筛选

- 搜索范围：门店名称、分店名、品牌、别名、曾用名、地址和公共电话。
- 筛选：品牌、城市或区域、菜系、营业状态、合作状态、准备情况、归档状态。
- 排序：最近修改、最近创建、名称；默认最近修改。
- 支持分页，筛选结果为空时显示清空筛选入口。
- 疑似重复基于名称、地址和电话组合提示，不阻止真实同名分店建档。

### 9.2 基础校验

| 类型 | 校验 |
| --- | --- |
| 数量 | 容量、桌数等为非负整数；明确为零必须是已知值 |
| 坐标 | 经度介于负 180 至 180，纬度介于负 90 至 90；成对填写 |
| 金额 | 非负，币种和单位明确；比例需有明确范围；免费与未知区分 |
| 日期 | 开始不晚于结束；允许开放式结束时间 |
| URL | 接受有效的 HTTP 或 HTTPS 链接；不自动访问和抓取 |
| 关联 | 所引用对象必须存在并属于同门店或明确共享的品牌对象 |
| 营业时段 | 同一适用范围内不允许未解释的重叠；正确处理次日结束 |
| 附件 | 单文件默认上限 50 MB，可在配置中调整；保存前显示格式或大小问题 |

跨对象的矛盾给出可定位提示；不能仅以“保存失败”代替具体错误。未明确核实的矛盾不自动改写数据。

### 9.3 保存与失败

- 分组保存，成功后显示结果；失败时保留输入，支持重试。
- 离开未保存页面时可保存、放弃或取消离开。
- 当前页面为空、加载失败、门店不存在分别提供明确状态。
- 同一工作站多标签页编辑时使用版本检查；遇到旧版本提交提示重新加载，不静默覆盖。
- 数据库迁移采用增量版本；保存资料及对应历史记录需保持原子性。

## 10 数据关系与模块接口

### 10.1 逻辑对象

| 对象组 | 关系 |
| --- | --- |
| 品牌与门店 | 品牌一对多门店；独立门店可无品牌关联 |
| 门店基础资料 | 门店关联位置、营业安排、设施和服务规则 |
| 菜单与产品 | 门店一对多菜单、产品和套餐；菜单与产品通过明细关联 |
| 价格与优惠 | 引用产品规格、套餐、包间或服务对象 |
| 媒体与证明 | 资产通过关联记录被业务对象和证据共同引用 |
| 渠道与快照 | 门店一对多渠道，渠道一对多不可覆盖快照 |
| 内部服务档案 | 门店一对多联系人、服务约定及沟通记录 |
| 横向元数据 | 核实记录、场景标签、资料版本、变更历史及资产引用 |

不要求每个业务分类对应一张表；是否拆表按查询、重复记录和历史需求决定。禁止用一个无约束大文本框承载全部商家资料。

### 10.2 对外读取能力

这里的“对外”指对其他业务模块，不表示公开互联网 API。实现优先提供 `src/modules/merchant/public.ts` 的进程内异步服务接口；页面需要 HTTP 路由时再做适配，不要求为每个模块单独部署服务。具体契约见 [API_CONTRACTS.md](API_CONTRACTS.md)。

| 操作 | 输入 | 输出与约束 |
| --- | --- | --- |
| 查询门店列表 | 搜索、筛选、分页 | 稳定门店 ID、摘要、状态、当前版本 |
| 查询当前资料 | 门店 ID、读取范围 | 当前资料、字段状态、核实与有效性、版本 |
| 查询历史资料 | 门店 ID、资料版本 | 当时可还原的资料，不混入当前值 |
| 查询已核实事实 | 门店 ID、可选版本和适用日期 | 当前有效且已核实的事实及来源；缺失项显式返回状态 |
| 查询渠道快照 | 门店 ID、可选渠道和时间范围 | 快照原文、采集时间、证据及更正关系 |
| 查询名称集合 | 门店 ID、版本 | 正式名称、别名、分店信息；曾用名单独返回 |
| 查询分类与明细 | 门店 ID、版本、分类、分页 | 覆盖全部 11 类资料及场景标签，不只返回列表摘要 |
| 查询关联素材与证据 | 门店 ID、资产或证据 ID、版本 | 元数据、关联对象及受控读取入口；不暴露机器绝对路径 |

A1 只能基于名称集合做候选匹配，不能仅因命中品牌名便确认具体分店。B1 读取已核实事实作为对照依据；后续模块不直接修改 F1 内部表或资产文件。

### 10.3 F1 与同事开发模块的责任边界

| 数据或能力 | 维护方 | 其他模块的使用方式 |
| --- | --- | --- |
| 门店标准事实、品牌关系、11 类档案 | F1 | 通过公开读取接口使用，不能维护第二份可编辑主数据 |
| 门店当前版本与历史资料 | F1 | 批次创建时先取得版本，后续多次读取固定该版本 |
| 渠道目录、原始快照 | F1 | B1 可通过 F1 的公开命令登记人工采集结果；不直接写 F1 表 |
| F1 素材与核实证据 | F1 | 引用资产 ID、证据 ID；底层文件由存储适配管理 |
| AI 原始回答和检测截图 | 检测模块 | 保存自己的记录；需要复用 F1 素材时引用原 ID |
| 一致性结论、修正任务和执行证据 | 优化模块 | 保存自己的记录；事实修正回到 F1 编辑流程 |
| 报告、指标、复测关联 | 报告或相应业务模块 | 引用版本、批次、问题及证据；不改写资料历史 |

后续模块确需新增渠道快照、关联证据或提出资料变更时，由 F1 暴露对应命令并校验归属、版本和历史。公开接口可读不等于其他模块可以随意覆盖标准事实。模块自己的结果、快照和历史留存不视为第二套商家主数据，但不能反向成为 F1 当前值。

### 10.4 交接与联调材料

F1 开发完成时必须同时交付：

1. `public.ts` 实际导出的类型与可调用接口，以及初始化或依赖注入说明。
2. 字段键、枚举、未知值、日期金额、分页、错误码和版本规则。
3. 同品牌两家分店及一家独立门店的虚构样例，含未核实、未知、不适用和内部资料。
4. 最小调用示例：查列表 → 选门店 → 固定版本 → 读取检测上下文、已核实事实、渠道及素材。
5. 联调验证：另一模块仅依赖公开入口即可读到已保存资料，编辑后旧版本稳定，外发投影不会夹带内部信息。

在同事开始集成前确认首批接口和字段；后续修改按兼容规则维护。当前仅有目录与占位导出，不表示这些能力已完成。

## 11 导出 备份与恢复

### 11.1 可公开资料导出

导出指定门店当前有效且明确可公开的结构化资料和选定公开素材。显示导出范围与资料版本；内部档案、待确认字段及未选证据不进入文件。本期至少支持可读的 Markdown 资料单和结构化 JSON，不承诺 GEO 报告或自动发布能力。

### 11.2 完整备份

导出整个工作站的 F1 数据包，包括品牌、所有门店、归档资料、明细、历史版本、证据、渠道快照、内部档案和本地附件。备份包含格式版本、导出时间、记录数量、资产清单及校验值。附件文件需实际包含在包内，不能只导出当前机器上的路径。

### 11.3 恢复规则

本期采用整体替换恢复，不提供按名称合并。恢复前先校验版本、引用关系、记录数量与附件完整性，显示将替换的数据范围，并自动生成当前数据备份；无法成功备份则不继续替换。操作者确认后整体恢复，失败时保持原数据可用。

恢复保留原 ID 和资料版本，不重新生成门店 ID。后续 A1、B1 等模块启用前，工作站备份范围必须扩展为跨模块一致备份，避免单独恢复 F1 导致其他模块引用失效。

## 12 验收标准

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| AC01 | 直接进入工作站 | 无需登录即可打开商家列表和操作资料 |
| AC02 | 最小建档 | 只填写最小字段可保存，其他信息显示未知，不伪造默认值 |
| AC03 | 同品牌多分店 | 两家同品牌门店有不同 ID，资料和附件互不串用 |
| AC04 | 疑似重复 | 同名同址时提示候选，但支持确认后创建；不自动合并 |
| AC05 | 全分类录入 | 11 类均可录入并保存至少一条代表性记录，刷新后可读取 |
| AC06 | 明细重复 | 可维护多份菜单、多道菜、多种规格、多个包间和多个渠道 |
| AC07 | 唯一事实归属 | 修改公共电话、包间价格等后，所有引用视图一致，不存在第二处独立主值 |
| AC08 | 字段状态 | 未知、不适用、已知否、已知零在保存和导出后仍可区分 |
| AC09 | 核实 | 无来源或核实时间不能标已核实；文字核实说明可作为证据 |
| AC10 | 改动已核实资料 | 新值回到未核实，旧值及证据可追溯 |
| AC11 | 跨午夜营业 | 17:00 至次日 02:00 正确保存和展示，最后点单校验正确 |
| AC12 | 日期例外 | 指定日期休息覆盖日常营业；重叠冲突能定位解决 |
| AC13 | 价格条件 | 套餐价、人均价、包间费和最低消费独立保存，金额币种单位不丢失 |
| AC14 | 渠道采集 | 同渠道两次采集形成两份快照，不覆盖原文，不自动修改标准事实 |
| AC15 | 平台指标 | 评分与评价数始终附带平台、采集时间及评分尺度 |
| AC16 | 附件复用 | 一个素材可关联多个对象；历史引用不会因停用素材而损坏 |
| AC17 | 公开范围 | 可公开导出不含联系人、合同、内部备注、待确认字段及默认原始证据 |
| AC18 | 场景标签 | 能查看判断依据；依据改变后提示待复核 |
| AC19 | 历史资料 | 当前资料及品牌介绍修改后，按旧版本读取仍得到旧值 |
| AC20 | 归档 | 归档不改变营业状态，恢复沿用原 ID 和历史 |
| AC21 | 查询 | 名称、别名、地址和电话可搜索，组合筛选与分页正确 |
| AC22 | 保存异常 | 保存失败保留输入；旧标签页提交不会覆盖较新资料 |
| AC23 | 数据持久化 | 刷新、关闭重开及服务重启后资料、附件和历史仍可用 |
| AC24 | 备份恢复 | 备份在空白实例恢复后，ID、数量、历史、快照和附件校验一致 |
| AC25 | 损坏备份 | 缺失附件、引用错误或版本不支持时拒绝替换，原数据可用 |
| AC26 | 模块边界 | F1 不出现伪造的检测结果、提及率、优化成效或人员权限入口 |
| AC27 | 全资料复用 | 11 类资料和场景标签均可通过公开接口结构化读取，而非只在页面可见 |
| AC28 | 无内部依赖联调 | 最小调用示例仅导入商家模块公开入口，不访问内部文件和数据表 |
| AC29 | 版本固定读取 | 首次获取版本后分次读取明细，期间编辑资料也不导致返回内容混用新旧版本 |
| AC30 | 内部读取与外发 | 内部核对可读所需未公开档案；外发投影排除内部及待确认资料，并保留过滤说明 |
| AC31 | 人工批量操作 | 复制周营业时段、连续新增明细及选定字段共用来源可用，不核实未选字段 |
| AC32 | 契约错误 | 不存在、版本不存在、归属不符及版本冲突返回明确错误，不伪装成空数据 |
| AC33 | 附件读取 | 其他模块凭资产 ID 可读取元数据和内容，不依赖开发者电脑的绝对文件路径 |

验收使用至少三家测试门店：同品牌两家分店及一家独立门店；覆盖未知字段、无包间、跨午夜营业、节假日例外、价格区间、多次渠道采集和归档恢复。测试资料明确标为样例，不作为真实商家事实。

## 13 开发拆分与完成条件

| 顺序 | 工作包 | 完成条件 |
| --- | --- | --- |
| 1 | 数据契约与持久化 | 先确定首批共享字段、读取投影与接口；门店 ID、品牌关系、状态、版本、关联规则和迁移可用 |
| 2 | 工作站外壳与基础建档 | 导航、列表、新增、详情、编辑、搜索、归档可用 |
| 3 | 完整资料录入 | 11 类字段、重复明细和唯一归属规则可用 |
| 4 | 核实与历史 | 字段状态、证据、公开范围、有效期、历史版本可用 |
| 5 | 资产与渠道 | 素材复用、不可覆盖快照、评分时点记录可用 |
| 6 | 场景与准备情况 | 依据关联、待复核和资料准备状态可用 |
| 7 | 导出与恢复验证 | 公开导出、完整备份、异常校验和恢复可用 |
| 8 | 同事联调与交接 | 类型、接口、虚构样例、调用示例和跨模块读取验证完成 |

这些工作包共同构成本期 F1，不代表只交付基础字段即可完成。批量表格导入、自动 OCR、地图可视化、模板文案和自动信息采集属于后续增强，不影响本期人工维护闭环。

最先达到的联调里程碑是：可人工新增与编辑基础资料、数据持久化、稳定门店 ID、固定版本读取以及可调用的共享接口。同事可基于该里程碑启动集成；完整 F1 仍需覆盖其余工作包，不以等待全部高级明细界面为由推迟基础契约确认。

## 14 与原开发文档的衔接

本文作为 F1 的产品需求基线。原 Demo 开发任务中“F1 已完成”的前提，只有在本期验收完成后才能成立；免登录、单人使用的范围以本文为准。原文中多人 AI Coding 的仓库协作规则属于开发过程约定，不作为工作站里的人员管理功能。

实现时沿用当前目录规范：`src/app/merchant/` 负责页面布局和交互，`src/modules/merchant/` 负责商家业务、校验和公开接口，`src/infrastructure/database/` 与 `src/infrastructure/storage/` 负责技术适配，`database/migrations/` 负责版本化迁移。其他 GEO 模块按需实现，F1 不为尚未开发的方法建立空执行框架。

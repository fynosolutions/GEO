# Issue #4 实施与准备计划

日期：2026-11-04。依据：https://github.com/fynosolutions/GEO/issues/4 。状态：设计草案，尚未实现 #4；接口提议需与同事统一。基线：96e0110 的 #3 与本地 #5。不部署、不触发付费采集，不改动同事的业务代码。

## 目标与现有能力

在已确认门店身份的基础上，检查七类菜单渠道，提取原始菜名和价格，按证据确定菜单日期及新旧，并逐日比较各平台与 Google 的营业时间。所有结果可追溯到来源及抓取时间。

复用 backend/public.ts 的采集入口、Google 身份解析、matched 门店校验、Apify 执行与取消能力。保留当前商户十三字段 JSON；#4 输出独立分析文件，不向 price_level 填写菜品价格，不覆盖原始 hours。七类菜单渠道不是现有八个平台清单，不能以八平台采集完成代替七类覆盖。

当前缺口：官网 HTML/PDF/图片专用采集，菜单图片文字提取，七类渠道状态，菜单日期证据与精度，菜单价格记录，营业时间解析/比较，以及与 #5 的菜单版本对接。现有 Actor 是否包含菜单必须检查真实输出后确认，不能从 Actor 名称推断。

## 分工建议（待双方确认）

同事负责渠道发现、网页/PDF/图片取证和菜品提取；本侧负责日期与营业时间规则、输出契约、#5 对接及验收。共享文件 backend/public.ts、config/apify.json、docs/API_CONTRACTS.md 指定一人整合，其他工作放各自新增目录。使用独立 codex/issue4-* 分支，通过小范围提交合并；不覆盖同事未完成工作。

## 第一步：冻结输出与判断契约

建议新增 backend/menu-audit/，提供 public.ts、README.md；内部划分 discovery、extractors、dates、hours、prices、report。建议命令 collect:details，输出 out/details/<store-id>/<run-id>/ 下的 channels.json、menus.json、prices.json、hours.json、summary.json。这些名称及封装属于提案，不是 Issue 已指定字段。

必须保留的菜单字段：channel、url、format（html/pdf/image）、menu_date、date_source、fetched_at。
必须保留的营业时间字段：platform、day、open、close、google_open、google_close、diff_minutes、verdict。

另需约定：
- 七类渠道各有覆盖记录；found 与访问状态分开。blocked/error/not_checked 不能算已经证实没有菜单。一个类别发现多个来源时逐份记录，不用一个来源代表全类别。
- 拟新增证据属性：原始日期文字、日期精度、菜单标识、文件摘要、证据定位、门店匹配依据；在契约中明确，不能假称 Issue 原生字段。
- 菜品记录拟包含原始名称、规格、原始价格字符串、币种（只有明确时）、菜单引用及来源/抓取时间；不自动翻译或跨币种换算。
- hours 中无法比较时建议 verdict:null 并在伴随状态中说明原因，不能强塞入三种成功判断。分段营业用有序时间段表达，保留每日一行；需双方确认最终类型。
- diff_minutes 建议 close - google_close，负数为提前，正数为延后；开门时间差和分段差异另存分析属性。不要只比较关门而漏报开门变化。

## 第二步：先实现可独立验证的规则

### 日期与菜单版本

按 on_page → metadata → upload_date → unknown 选择证据。页面日期必须针对菜单，不能将版权年份当菜单日期。HTTP Last-Modified 只作用于当前菜单资源，不能取首页时间代表 PDF。保留元数据证据和获取时间。

menu_date 支持明确的年/月/日精度方案，例如 YYYY、YYYY-MM、YYYY-MM-DD；季节表述保存原文，未经约定不转换成某个具体日期。不能把 Updated 2026 写成 2026-01-01。

按抓取日减去 12 个日历月设边界：日期明确时，边界内 fresh，超过 stale；无日期 unknown_date。只有年份/月时用可能日期区间推理：整个区间均旧才判 stale，整个区间均新才判 fresh，跨界时返回待确认的日期精度状态，不能将有日期但不精确混称无日期。未来日期应标异常、不直接判新。上述区间与额外状态方案需先确认。

跨渠道差异超过 6 个日历月才标 channels_out_of_sync。针对同一菜单类型/用途比较，堂食与酒单不是自动可比；精度不足时只在区间也能证明超阈值时作确定结论。列出最旧来源和证据。fresh/stale 表示按 Issue 规则的日期年龄，不代表已核验现实价格有效性。

### 营业时间

以同一门店、同一周表口径的 Google 时间为基准，转换为门店本地时区下的区间，仅用于分析；原始 hours 保留。
- 完全相同：一致。
- 外卖平台开门/分段均可比，且关门提前大于 0、至多 30 分钟：外卖常规提前。
- 外卖提前超过 30 分钟或晚关：不一致；开门差异也不能被关门宽限掩盖。
- 非外卖平台任一有效时段不同：不一致。
- 缺失、只写当前开关门、假日表与常规表混用、时区不明：无法比较，列原因。

处理 12AM/12PM、跨午夜、分段、24小时、休息日；跨午夜归属于开门当天，避免差出 24 小时。Google 缺失不换其他平台作基准。

## 第三步：分批接渠道与价格

七类覆盖目录：官网 HTML；官网 PDF/图片；Google Menu/照片；Yelp 菜单/照片；DoorDash/Uber Eats/Grubhub；OpenTable/Resy 等；Facebook/Instagram。

先接官网 HTML、可提取文字的 PDF、已有 Actor 明确返回的结构化菜单。随后接扫描 PDF/图片及平台照片。通过配置开启选定的图片文字识别方案，不假设现有 Apify Token 包含 OCR 能力。无日期图片仍可提取价格，但日期必须 unknown。

每份菜单继承已验证门店的链接关系或独立匹配证据，防止连锁其他分店菜单混入。链接发现只找候选，搜索摘要不充当价格证据。已认证官网菜单链接也应检查分店适用性。

HTML/PDF/图片处理设大小、页数、超时与请求限制，限制到公开 HTTP(S) 资源并检查重定向目标。不登录客户账户、不绕过访问限制。访问失败保留证据和原因，其他渠道继续。

价格按菜名+规格+来源逐条原样保存；套餐、加料、起价、价格区间不得压成一个普通单价。同名不代表同规格，不强制跨平台合并。先满足十道菜逐项人工核对，再扩展自动关联。

## 第四步：与 #5 集成

backend/weekly/menus.ts 目前只允许完整日期且按相同 source_url 对比，必须修订：
1. 接收年/月/日精度及日期来源，不填造日期；旧接口通过明确版本迁移保留可读。
2. 使用稳定菜单标识和来源类别；URL/文件摘要变化另记版本替换，不能因 URL 变了就漏报，也不能将不同菜单强行配对。
3. 将 #4 的 url 映射到 #5 source_url，保留 fetched_at 与来源证据；生成当次 sidecar，不手工维护一份过期文件。
4. weekly worker 同次获取 #4 结果；已有 --menus 用于文件导入/测试。菜单失败不使商户基本信息丢失。
5. 工作流与 CLI 接入实际生成 sidecar；验收 raw snapshot → details → weekly report 可追踪。部署仍等合并后。

图片识别：先验证现有工具/Actor 能力；若缺少，比较本地 OCR 与外部识别服务后确定一种。外部服务需对应密钥/预算，本地 OCR 需安装依赖，不能未经确认就增加付费调用。基础规则和 HTML/PDF 文本工作不依赖此选择。

不需要先租服务器、不需要先启用 Actions、无需平台客户登录凭据。
